# Формат входа

Вход — один JSON-документ (`problem.json`). Схема: [`schemas/problem.schema.json`](../schemas/problem.schema.json),
она генерируется из Pydantic-моделей в `src/expsched/contract/io_models.py` (`make schema`). Неизвестные поля —
ошибка схемы.

```json
{
  "time_unit": "hour",
  "cluster": {
    "workers": [
      {"id": "node-A", "resources": {"gpu": 4}, "labels": {"gpu_type": "a100"}},
      {"id": "node-B", "resources": {"gpu": 2}}
    ]
  },
  "tasks": [
    {"id": "prep", "duration": 2, "resources": {"gpu": 1}},
    {"id": "train", "kind": "train", "duration": 8, "resources": {"gpu": 4},
     "dependencies": ["prep"], "checkpoint_interval": 2, "constraints": {"gpu_type": "a100"}},
    {"id": "eval", "kind": "eval", "duration": 1, "resources": {"gpu": 1},
     "dependencies": ["train"], "priority": 6, "deadline": 14}
  ],
  "events": [
    {"time": 5, "type": "worker_down", "worker": "node-A"},
    {"time": 9, "type": "worker_up", "worker": "node-A"}
  ],
  "policy": {"name": "priority"}
}
```

Здесь `train` может идти только на node-A. Узел падает в 5: сохранены 2 единицы работы из 3, задача ждёт
возврата узла (`WAIT_WORKER_DOWN`), продолжает в 9 и заканчивается в 15, а `eval` опаздывает на 2.

Время — целые числа в единицах `time_unit` (`minute` по умолчанию, `hour`, `second`), отсчёт от 0.
Необязательное `name` (до 128 символов) — как показывать вход в списках прогонов; оно входит в `input_hash`.

## Узлы

| Поле | Тип | По умолчанию | |
|---|---|---|---|
| `id` | строка | — | `[A-Za-z0-9][A-Za-z0-9_.-]*`, до 128 символов |
| `resources` | `{имя: целое ≥ 0}` | — | имена ресурсов произвольные: `gpu`, `cpu`, `ram_gb`, … |
| `labels` | `{строка: строка}` | `{}` | по ним задачи выбирают узлы |

Ресурс, которого нет у узла, равен 0. Нужен хотя бы один узел.

## Задачи

| Поле | Тип | По умолчанию | |
|---|---|---|---|
| `id` | строка | — | как у узла, уникален |
| `kind` | `data`, `train`, `eval`, `infer`, `other` | `other` | только для отображения |
| `duration` | целое ≥ 1 | — | время работы без прерываний |
| `resources` | `{имя: целое ≥ 0}` | `{}` | занимаются на одном узле целиком |
| `priority` | 0–10 | 1 | классы: 8–10 critical, 5–7 high, 2–4 normal, 0–1 low |
| `deadline` | целое | нет | момент, к которому задача должна закончиться |
| `release_time` | целое | 0 | раньше этого момента задача не стартует |
| `dependencies` | список id | `[]` | задача стартует после окончания всех зависимостей |
| `checkpoint_interval` | целое ≥ 1 | нет | при прерывании сохраняется работа до последнего чекпоинта |
| `max_retries` | 0–20 | 2 | сколько прерываний отказами узла задача переживёт |
| `constraints` | `{строка: строка}` | `{}` | узел должен иметь все эти метки с теми же значениями |
| `preemptible` | bool | `false` | можно ли прервать задачу ради другой |

Узел подходит задаче, если у него хватает ёмкости и есть все метки из `constraints`.

## События

| `type` | Поля | |
|---|---|---|
| `worker_down` | `time`, `worker` | узел отказал: его задачи прерываются |
| `worker_up` | `time`, `worker` | узел вернулся пустым |
| `submit_task` | `time`, `task` | задача появляется в момент `time`; `task` — объект задачи |

Поданная задача может зависеть от задач входа и от поданных раньше. Ошибки поданной задачи (неизвестная
зависимость, не хватает ни одного узла) проверяются в момент подачи и дают ей статус INFEASIBLE.

## Политика

| Поле | По умолчанию | |
|---|---|---|
| `name` | `priority_backfill` | `fifo`, `fifo_skip`, `priority`, `priority_backfill`; `cpsat` пока не реализована |
| `aging` | 360 | для `priority` и `priority_backfill`: класс растёт на 1 за каждые `aging` единиц ожидания; `null` — выключено |
| `validation_mode` | `lenient` | `strict` — при любой ошибке входа прогон не запускается |
| `preemption` | `deadline_only` | `never` — не вытеснять; `deadline_only` — [вытеснять ради дедлайна](scheduling.md#вытеснение-ради-дедлайна); `priority` пока не реализован |
| `max_preemptions_per_task` | 1 | сколько раз можно вытеснить одну задачу |
| `min_runtime_before_preempt` | 30 | сколько задача должна проработать, прежде чем её можно вытеснить, в единицах `time_unit` |
| `max_forecast_tasks` | 1000 | [прогноз перепланирования](scheduling.md#перепланирование) строится, если задач (вместе с поданными) не больше; 0 — не строить |

`objective`, а также `seed` и `mode` верхнего уровня зарезервированы и на результат пока не влияют.

## Проверка входа

Ошибки (`E…`) и предупреждения (`W…`) возвращаются как данные: `{code, level, detail, hint}`.

| Код | Название | Когда |
|---|---|---|
| E001 | SCHEMA_INVALID | документ не соответствует схеме |
| E010 | UNKNOWN_DEPENDENCY | зависимость от несуществующей задачи |
| E011 | SELF_DEPENDENCY | задача зависит от самой себя |
| E012 | DEPENDENCY_CYCLE | цикл зависимостей; `detail` содержит один цикл |
| E020 | RESOURCE_EXCEEDS_ANY_WORKER | требование больше ёмкости любого узла, подходящего по меткам |
| E021 | NO_MATCHING_WORKER | нет узла с нужными метками или со всеми ресурсами сразу |
| E030 | DEADLINE_UNREACHABLE | дедлайн не успеть даже при неограниченных ресурсах |
| E040 | UNKNOWN_WORKER | событие узла, которого нет в кластере |
| E050 | NO_LIVE_CAPACITY | в конце прогона: задача готова, но все подходящие ей узлы недоступны |
| E070 | DURATION_NOT_POSITIVE | `duration` меньше 1 |
| W060 | DUPLICATE_EDGE | зависимость указана дважды |

В режиме `lenient` задачи с E010, E011, E012, E020, E021 получают INFEASIBLE, их потомки — BLOCKED, события
с E040 отбрасываются; остальное планируется. Задача с E030 планируется как обычно и, скорее всего, опоздает.

Лимиты: 20 МБ на документ, 100 000 задач, 1 000 000 зависимостей.
