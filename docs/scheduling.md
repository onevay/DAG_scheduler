# Как строится расписание

Прогон (`expsched.pipeline.run`) идёт в четыре шага:

1. **Проверка входа** — граф, ресурсы, события, дедлайны ([коды](input.md#проверка-входа)). В режиме `strict`
   при ошибках прогон на этом заканчивается со статусом INFEASIBLE.
2. **Карантин** — задачи с ошибками и их потомки убираются из плана.
3. **Симуляция** выбранной политикой. Результат симуляции — журнал событий.
4. **Разбор журнала** — проверка расписания, метрики, интервалы ожидания. Эти модули видят только вход
   и журнал и не зависят от движка.

## Симуляция

Время дискретное. Движок держит очередь событий и обрабатывает их эпохами: все события ближайшего момента,
затем одно решение политики, затем применение решений. Каждое решение проверяется: старт неготовой задачи,
на недоступном или неподходящем узле или сверх свободных ресурсов — исключение `InvalidDecision`, так что
ошибка политики не превращается в неверное расписание.

События одного момента обрабатываются в порядке:

1. окончания задач;
2. отказы узлов;
3. возвраты узлов;
4. подача задач и наступление `release_time`;
5. решение политики.

Поэтому задача, закончившаяся ровно в момент отказа узла, считается выполненной, а освободившееся место
доступно задачам этой же эпохи. Внутри одного класса события упорядочены по номеру, так что прогон
детерминирован: тот же вход и та же политика дают тот же журнал и тот же `result_hash`.

Статусы задачи: PENDING → READY → RUNNING → SUCCEEDED. Финальные статусы без выполнения: FAILED (кончились
ретраи), BLOCKED (не выполнится одна из зависимостей), INFEASIBLE (ошибка входа).

## Политики

Политика — чистая функция снимка состояния: получает готовые задачи, свободные ресурсы и анализ графа,
возвращает решения: старты, резервы и вытеснения. Вытеснения применяются первыми, затем остальные решения
по порядку. Резерв ресурсов не занимает: политика пересчитывает его каждую эпоху, а движок проверяет решение
и пишет его в журнал. Узел для задачи у всех политик выбирается best-fit:
самый тесный по доминирующему ресурсу задачи, чтобы крупные свободные блоки оставались крупным задачам.

| Политика | Порядок очереди | Если задаче сейчас нет места |
|---|---|---|
| `fifo` | момент готовности, `release_time`, id | очередь останавливается |
| `fifo_skip` | так же | задача пропускается |
| `priority` | класс, запас до дедлайна, длина оставшейся цепочки, `release_time`, id | задача пропускается |
| `priority_backfill` | как у `priority` | первая такая задача получает резерв, остальные стартуют, только если не отодвигают его |

Запас до дедлайна — `LST − t`, где LST — поздний старт по критическому пути; у задач без дедлайна он
бесконечен. С `aging` ждущая задача поднимается на класс за каждые `aging` единиц ожидания, но не выше high:
critical назначает только человек.

`priority_backfill` (EASY backfilling) не даёт крупной задаче голодать за потоком мелких. Первая задача
очереди, которой сейчас нет места, получает резерв: самый ранний момент `t_res` и узел, где для неё
освободится место по окончаниям выполняющихся задач. Остальные задачи стартуют, если идут на другом узле,
заканчиваются к `t_res` или помещаются в то, что останется на узле резерва после неё (`extra`). Такой старт
пишется с причиной `{code: BACKFILL, head, t_res}`. Пока нет отказов и в очереди не появляются задачи выше,
задача с резервом стартует не позже `t_res`.

## Отказы узлов и вытеснение

На `worker_down` каждая задача узла прерывается. Сохраняется работа до последнего чекпоинта:

```
saved = checkpoint_interval · ⌊elapsed / checkpoint_interval⌋     # без чекпоинта — 0
lost  = elapsed − saved
```

Задача снова становится готовой с остатком `duration − Σ saved` и может продолжить на любом подходящем узле.
Если прерываний больше `max_retries`, задача получает FAILED, а все её потомки — BLOCKED. На `worker_up` узел
возвращается пустым.

Вытеснение прерывает попытку так же, но только у задачи с `preemptible: true`, и не расходует `max_retries`:
у него свой счётчик, ограниченный `max_preemptions_per_task`. Политик, которые вытесняют, пока нет.

Пример из `scenarios/failure.json`: `pretrain_vit` (8 ч, чекпоинт каждые 2 ч) стартует на node-A в 2, узел
падает в 5. Сохранено 2 ч, потерян 1 ч, осталось 6 ч; вторая попытка стартует в 5 на node-B.

## Почему задача ждёт

Для каждой нестартовавшей задачи движок ведёт причину ожидания и пишет запись `WAIT`, когда она меняется.

| Код | Значение | `detail` |
|---|---|---|
| WAIT_DEPS | не закончились зависимости | `pending` — какие |
| WAIT_RELEASE | ещё не наступил `release_time` | |
| WAIT_WORKER_DOWN | все подходящие узлы недоступны | `eligible` |
| WAIT_RESOURCES | задача не помещается ни на один работающий узел | `need`, ближайший по свободному месту узел |
| WAIT_RESERVATION | задача помещается, но её придержали ради резерва другой задачи | `head`, `worker`, `t_res` |
| WAIT_PRIORITY | место было, но политика отдала его другим | `started` — кому |

В результате прогона они собраны в интервалы `{code, from, to, detail}` по каждой задаче.

## Журнал

Список записей `{seq, t, type, …}` в порядке появления.

| `type` | Поля |
|---|---|
| `SUBMIT` | `task`, `priority`, `deadline` |
| `READY` | `task` |
| `WAIT` | `task`, `code`, `detail` |
| `START` | `task`, `worker`, `attempt`, `resume_from`, `reason` — почему политика выбрала задачу |
| `RESERVE` | `task`, `worker`, `t_res` — политика обещает начать задачу на узле не позже `t_res`; пишется, когда резерв меняется |
| `FINISH` | `task`, `attempt`, `worker` |
| `WORKER_DOWN`, `WORKER_UP` | `worker` |
| `INTERRUPTED` | `task`, `attempt`, `worker`, `cause` (`WORKER_DOWN`, `PREEMPT`), `saved`, `lost`, `remaining`; при вытеснении — `reason` от политики |
| `BLOCKED` | `task`, `by` — задача, из-за которой |
| `DIAGNOSTIC` | `code`, `task`, … — проблемы, найденные во время прогона (STUCK, E050, ошибки поданных задач) |

## Проверка расписания

`verify(problem, log)` восстанавливает попытки по журналу и проверяет:

| | |
|---|---|
| I1 | успешная попытка проработала ровно оставшуюся работу |
| I2 | старт не раньше окончания всех зависимостей |
| I3 | загрузка узла в любой момент не больше его ёмкости |
| I4 | попытка не идёт, пока узел недоступен |
| I5 | старт не раньше `release_time` и подачи |
| I6 | узел подходит задаче |
| I7 | после успешной попытки других нет |
| I11 | попытка продолжает ровно с сохранённой работы |
| I12 | попытки одной задачи не пересекаются |
| C9 | вытеснена только задача с `preemptible: true` |
| C10 | вытеснений задачи не больше `max_preemptions_per_task` |

Нарушения возвращаются строками вида `I3 node-B t=12: …` в поле `violations` результата.

## Метрики

| | |
|---|---|
| `makespan` | окончание последней задачи |
| `lower_bound`, `gap_to_lb` | нижняя граница makespan (максимум из критического пути, объёма работы по каждому ресурсу на суммарную ёмкость и оценки по крупным GPU-задачам; отказы не учтены) и `(makespan − LB) / LB` |
| `deadline_misses` | по классам; задача с дедлайном, которая не закончилась, — тоже пропуск |
| `weighted_tardiness` | Σ 2^класс · опоздание |
| `utilization_gpu` | полезная GPU-работа / ёмкость работающих узлов за makespan |
| `lost_work_gpu` | GPU · время, потерянное прерванными попытками после последнего чекпоинта |
| `mean_wait` | по выполненным задачам: от первой готовности до окончания минус `duration` — ожидание очереди и время, потерянное на прерываниях |
