# Протокол агента

Агент — отдельный процесс на машине, где идут задачи (на ноутбуке — один). Он получает от планировщика
команды «запустить попытку», «остановить», «сохранить чекпоинт», запускает контейнеры, следит за ними и
сообщает планировщику, что с ними случилось. Планировщик по этим событиям ведёт прогон: окончание контейнера —
окончание попытки, его падение или нехватка памяти — отказ, пропавший агент — отказ его узлов.

Сообщения описаны Pydantic-моделями в `src/expsched/contract/agent.py` и JSON Schema
[`schemas/agent.schema.json`](../schemas/agent.schema.json) (`make schema`). Версия протокола — `1`.
Прогон на агентах запускается `POST /v1/runs` со входом в режиме `emulate` — см.
[REST API](api.md#прогон-на-агентах).

## Запуск

```bash
uv run python -m expsched.agent --scheduler http://127.0.0.1:8000 --id laptop
```

| Параметр | По умолчанию | |
|---|---|---|
| `--id` | — | id агента, как в поле `agent` узлов |
| `--runtime` | `docker` | `docker`, `podman` или `fake` — подделка без контейнеров для проверок |
| `--workload-image` | `expsched-workload:local` | образ встроенной нагрузки (`make workload-image`) |
| `--state` | `.expsched-agent` | каталог журнала `state.jsonl` и чекпоинтов задач |
| `--cpu`, `--ram-mb`, `--gpu` | машина минус запас | ёмкость под задачи: ядра минус одно, ОЗУ минус 2 ГиБ, GPU по `nvidia-smi` |
| `--max-containers` | 4 | сколько попыток одновременно |
| `--allow-image` | — | разрешённый образ задач; можно повторять |

Журнал — единственное состояние агента: команды, id контейнеров, события и подтверждения. Каждая запись
сбрасывается на диск до того, как агент на неё опирается. После перезапуска агент проигрывает журнал и
сверяется со средой: свою попытку без контейнера запускает заново (её команда уже подтверждена и не придёт
снова), контейнер, запущенный перед падением, подхватывает, чужие и законченные останавливает, пропавшие
сообщает как `lost`. Недописанная последняя строка журнала (падение посреди записи) пропускается.

## Контейнеры

Docker и Podman агент вызывает через их CLI — у них одинаковые `run`, `inspect`, `ps`, `kill`, `rm`.
Контейнер попытки называется `expsched-<run>-<task>-<attempt>` и помечен метками `expsched.agent` и
`expsched.attempt`: по ним агент находит свои контейнеры после перезапуска и не трогает чужие. Запуск:

- лимиты — `--cpus`, `--memory` (и столько же `--memory-swap`: без подкачки нехватка памяти — это OOM, а не
  медленная работа), `--gpus`;
- `--security-opt no-new-privileges`, `--cap-drop ALL`; на Linux — от пользователя агента, чтобы писать в
  каталог чекпоинтов; встроенная нагрузка — без сети;
- каталог чекпоинтов задачи смонтирован в `/checkpoint`, параметры работы — в переменных `EXPSCHED_*`;
- чекпоинт по команде — сигнал `SIGUSR1`, остановка — `rm -f`; законченный контейнер агент убирает сам.

Встроенная нагрузка (`src/expsched/agent/workload.py`, образ — `containers/workload/Containerfile` на
`python:3.12-slim` от непривилегированного пользователя) делает `work` единиц по `time_scale_ms` мс, пишет
чекпоинты, продолжает с сохранённого и держит в памяти `EXPSCHED_USE_RAM_MB` МиБ — так можно показать OOM.
`make test-docker` собирает образ и гоняет тесты с настоящим Docker (в CI — задача `docker`).

## Обмен

Связь всегда начинает агент — обычным HTTP к планировщику. Поэтому он работает и на той же машине, и из-за NAT,
а планировщику не нужно знать адрес агента.

```
агент                                        планировщик
  │ POST /v1/agents/{id}/hello   Hello  ─────▶│  ёмкость, среда, что уже идёт
  │◀───────────────────────────── HelloAck ───│  таймауты, с какого номера слать события
  │ POST /v1/agents/{id}/poll    Poll   ─────▶│  до wait_s секунд ждёт команд
  │◀──────────────────────────── PollReply ───│  команды с номерами > acked_command_id
  │ POST /v1/agents/{id}/events  EventsBatch ▶│  события подряд по номерам
  │◀──────────────────────────── EventsAck ───│  следующий ожидаемый номер
```

`id` агента — как id узла: `[A-Za-z0-9][A-Za-z0-9_.-]*`. Все запросы — с заголовком
`Authorization: Bearer <EXPSCHED_AGENT_TOKEN>`; без переменной на сервере агентский API выключен, ответ на
неверный или отсутствующий токен — 403 `FORBIDDEN`. Пачка событий с пропущенным номером — 409 `EVENT_GAP`
(агент досылает с номера из сообщения). В `hello` агент сообщает и свою нумерацию — первое неподтверждённое
событие (`next_event_seq`) и последнюю записанную команду (`acked_command_id`): планировщик, который этого
агента ещё не видел (например, сам перезапустился), продолжает её, а не ждёт событие 0 и не шлёт команду 1,
которую агент пропустил бы как уже записанную. Узел кластера во входе указывает своего агента
полем `agent`; один агент может обслуживать несколько узлов.

## Команды

| `kind` | Что делать |
|---|---|
| `start` | запустить попытку `run_id:task:attempt` на узле `worker` с лимитами `limits`; `container` — образ, команда, окружение; без него — встроенная нагрузка на `work` единиц времени модели по `time_scale_ms` мс, с чекпоинтами каждые `checkpoint_interval` и продолжением с `resume_from` |
| `stop` | остановить попытку; `reason` — `preempt`, `worker_down` или `cancel` |
| `checkpoint` | сохранить чекпоинт сейчас, не дожидаясь интервала |

Номера команд (`command_id`) растут без пропусков для каждого агента. Агент записывает команду в свой журнал и
только потом подтверждает её в следующем опросе (`acked_command_id`); планировщик повторяет неподтверждённые.
Команду с уже записанным номером агент пропускает — потерянный ответ не запустит контейнер дважды.

Лимиты контейнера берутся из ресурсов задачи: `cpu` → `--cpus`, `ram_mb` → `--memory` (МиБ), `gpu` → `--gpus`.
Попытка, которой не хватит ёмкости агента, отклоняется событием `rejected`.

## События

| `type` | Когда | Обязательно |
|---|---|---|
| `accepted` | команда `start` принята, контейнер создаётся | |
| `rejected` | команду `start` выполнить нельзя | `detail` |
| `started` | контейнер запущен | |
| `checkpoint` | сохранён чекпоинт: сделано `progress` единиц работы | `progress` |
| `exited` | контейнер завершился; 0 — попытка выполнена | `exit_code` |
| `oom` | контейнер убит за превышение `--memory` | |
| `killed` | контейнер остановлен командой `stop` | |
| `lost` | агент потерял контейнер (например, его удалили вручную) | `detail` |

Номера событий (`seq`) у агента идут подряд с нуля, в пачке — без пропусков. Планировщик принимает пачку,
пропускает события с уже принятыми номерами и отвечает следующим ожидаемым номером; пачка с пропуском
номера отклоняется. После перезапуска агент узнаёт из `HelloAck.next_event_seq`, с какого события досылать;
если планировщик помнит этот id дальше журнала агента (журнал новый или потерян), агент продолжает нумерацию
с его номера.

## Прогон на агентах

Часы модели — часы стены в масштабе `time_scale_ms` входа (мс на единицу времени модели). Каждый узел
кластера должен назвать своего агента (`agent`). Решения политики становятся командами: START — `start`
с остатком работы, сохранённым прежними попытками и лимитами из ресурсов задачи; вытеснение и отказ узла —
`stop`. События агента становятся фактами движка: `exited` с кодом 0 — окончание, с другим кодом, `lost`
и `rejected` — сбой `FAILED`, `oom` — сбой `OOM` (оба расходуют ретрай), `checkpoint` — сохранённая работа.
Окончание приходит, когда его заметил агент, поэтому длительности попыток — настоящие: проверка I1 («попытка
шла ровно остаток работы») для таких прогонов не делается. Если узлы лежат, а задачи не закончены, прогон
ждёт возвращения агента.

Посмотреть без Docker: сервер с токеном (`EXPSCHED_AGENT_TOKEN=dev-token make run`), агент
`EXPSCHED_AGENT_TOKEN=dev-token uv run python -m expsched.agent --scheduler http://127.0.0.1:8000 --id laptop
--runtime fake`, в клиенте — пример `laptop`, экран «Контейнеры», режим «Эмуляция» и «Запустить на агентах».

## Таймауты и отказ агента

Пустой опрос планировщик держит `poll_timeout_s` секунд. Если агент не опрашивал дольше
`heartbeat_timeout_s`, его узлы считаются упавшими (`worker_down`), а попытки на них — прерванными.
Вернувшийся агент снова шлёт `hello` со списком того, что у него идёт (`running`); попытки, которые
планировщик уже считает прерванными, агент останавливает по команде `stop`.

## Чекпоинты

Чекпоинт — на уровне приложения. Агент монтирует в контейнер каталог задачи и передаёт его путь в переменной
`EXPSCHED_CHECKPOINT_DIR`; задача пишет туда своё состояние и `checkpoint.json` вида `{"progress": n}`. Агент
замечает новый `checkpoint.json` и шлёт событие `checkpoint`. Следующая попытка той же задачи получает тот же
каталог и `resume_from` — сохранённую работу. Встроенная нагрузка делает всё это сама.

## Безопасность

Агент исполняет образы из входа, поэтому:

- по умолчанию разрешён только образ встроенной нагрузки, другие — по списку в конфигурации агента;
  неразрешённый образ — событие `rejected`;
- контейнеры запускаются без привилегий, только с лимитами из ресурсов задачи;
- запросы агента подписываются токеном из `EXPSCHED_AGENT_TOKEN` (общим для планировщика и агента), без
  токена агентский API отключён; по умолчанию и планировщик, и агент слушают только 127.0.0.1.
