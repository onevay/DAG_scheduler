# Интерфейс

Интерфейс — JS-клиент [REST API](../docs/api.md) в [`web/`](web/README.md): React, TypeScript, Vite. Вид — по
макету, токенам и анимациям из [`design/`](design/README.md). Клиент не импортирует `expsched` и не хранит
своего состояния на сервере: всё, что он показывает, берётся из результата и журнала прогона; черновик входа
живёт в `localStorage` браузера. Вход, результат и запись журнала описаны JSON Schema в `../schemas/`
(`problem`, `result`, `event`), типы клиента генерируются из `schemas/openapi.json`.

```bash
make web-install   # один раз: зависимости клиента, нужен Node.js 20
make run           # сборка клиента и API одним сервером на http://127.0.0.1:8000
```

Для разработки — `make api` и `make web-dev` в двух терминалах: клиент на http://127.0.0.1:5173 с горячей
перезагрузкой, запросы `/v1` уходят на API. Всё одним контейнером — `docker compose up --build`.

## Экраны

- **Обзор** — последние прогоны, метрики выбранного, загрузка узлов и матрица занятости по часам; новый сценарий
  из примера.
- **Сборка** — вход: пример из `scenarios/`, свой `problem.json` или пустой; граф задач, свойства задачи,
  ресурсы (ядра, ОЗУ в ГБ, GPU — все необязательны), зависимости; проверка входа с подсветкой задач с ошибками; все параметры политики (вытеснение,
  старение очереди, прогноз перепланирования, мягкая или строгая проверка). Выгрузка собранного входа.
  Длительность задачи — известна или неизвестна: у неизвестной — оценка (медиана и разброс, обе
  необязательны) и до запуска видно, какой она получится и откуда (своя, по истории, по задачам того же типа,
  умолчание типа); закон ускорения по числу CPU/GPU (Амдал или степенной) с параметром.
- **Кластер** — карточки узлов со скоростью (во сколько раз быстрее эталона), ядрами, ОЗУ и GPU, события узлов на шкале и списком, интервалы недоступности.
- **Прогон** — метрики, диаграмма Ганта с проигрыванием по времени (отказы затенены, потерянная работа
  заштрихована, резервы отмечены), лента журнала, таблица задач с попытками и главной причиной ожидания,
  перепланирования, оценка против факта у задач без длительности (ожидали, p80, факт, ошибка, сколько уложилось
  в p80); у прогона shadow — план рядом с фактом; «Проиграть журнал» — проверка, что политика на тех
  же фактах принимает те же решения; выгрузка `result.json` и `events.jsonl`.
- **Объяснения** — разложение makespan по критической цепочке, шаги цепочки с причинами ожидания, простой
  по узлам и часам по выбранному ресурсу с фильтром причин, итог по кодам.
- **Сравнение** — прогоны всех реализованных политик на одном входе, капсулы по метрике (загрузка и потери — по выбранному ресурсу), места по цели, профиль-«цветок»;
  **what-if** — вмешательства (узел, чекпоинт, вытесняемость, приоритет, дедлайн, без отказов) и карточки
  с дельтами к исходному прогону.
- **Контейнеры** — режим прогона (симуляция, эмуляция, shadow, replay) и масштаб времени; агенты, которых
  видит сервер (среда, ёмкость, на связи ли, занятые контейнеры), запуск агента на машине сервера (среда,
  ёмкость автоматически или заданная; при неготовности среды — вывод проверки), его журнал и остановка, и выбор агента для каждого узла; прогоны на
  агентах, которые помнит сервер; запуск на агентах; у идущего прогона — карточки попыток с состоянием, сохранённой работой и номером
  попытки (fence) — у задачи без длительности кольцо идёт до квантиля 0,8, полоса в его конце — где задача
  закончится скорее всего, процент — со знаком «≈»; фильтр по состоянию, журнал выбранной попытки с
  уточнениями оценки, «Сохранить чекпоинт», «Уронить/Вернуть
  узел» и отмена прогона; у идущего контейнера — потребление CPU и ОЗУ против ресурсов задачи (у предела
  памяти — предупреждение) и хвост его журнала (обновляется раз в 2 с, пауза, копирование); в режиме shadow —
  план рядом с фактом по задачам с причиной расхождения.
- `/system` — живая дизайн-система: все компоненты во всех состояниях.
